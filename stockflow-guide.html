Introdução

Este documento é um guia passo a passo para construir a StockFlow API — um sistema de gerenciamento de loja virtual que controla produtos, estoque, fornecedores e pedidos de compra. O projeto aplica os mesmos conceitos do curso de NestJS com Clean Architecture, mas em um domínio diferente para fixar o aprendizado.

📝 Como este documento foi criado

O conteúdo da StockFlow não foi inventado do zero. Ele foi extraído do curso de NestJS na Udemy, aula por aula, e depois reorganizado para um domínio de loja virtual.

A extração foi feita com o plugin do Cloud Code no Chrome: em cada ação do curso (criar entidade, montar use case, ligar Prisma, escrever teste, etc.), o plugin gerava um resumo do que estava sendo feito naquela aula. Esses resumos viraram o mapa das seções — o que o curso ensina, em que ordem, e o que cada etapa produz.

Com essa base, o material foi separado por camada (domínio, aplicação, infraestrutura, testes, auth, docs, deploy) e traduzido para a StockFlow: o User do curso vira Product, Supplier, Stock e PurchaseOrder. Cada seção deste guia segue o mesmo fluxo da aula original, com o card O que o curso ensina e o desafio correspondente no domínio da loja.

DDD — Entendendo as Camadas de Verdade

Antes de escrever qualquer código, você precisa entender por que o projeto está organizado dessa forma. Vamos usar uma analogia do mundo real para tornar isso concreto.

A analogia da pizzaria

Imagine que você vai montar uma pizzaria. Ela tem três áreas bem separadas, cada uma com uma responsabilidade clara:

🍕 A cozinha — equivale ao DOMÍNIO

É onde ficam as receitas e as regras do negócio. O chef sabe que uma pizza Margherita leva molho, mussarela e manjericão. Ele sabe que massa crua não pode ser servida. Essas regras existem independente de o cliente ter pedido pelo telefone, pelo app ou pessoalmente.

A cozinha não se preocupa com como o pedido chegou, se o pagamento foi no débito ou crédito, ou se o sistema usa PostgreSQL ou MongoDB. Ela só sabe fazer pizza do jeito certo.

Na StockFlow: a regra "preço de venda deve ser maior que preço de custo" e "SKU é imutável" vivem aqui. Não importa se o pedido veio de uma requisição HTTP, de um job agendado ou de um teste — a regra sempre vale.

📋 O gerente de pedidos — equivale à APLICAÇÃO

É quem coordena o fluxo de uma operação completa. Quando um pedido chega, o gerente verifica se o produto está disponível, confirma o pagamento, passa para a cozinha, e avisa quando está pronto. Ele não sabe fazer pizza — ele orquestra quem sabe.

O gerente não toca em detalhes técnicos — ele não liga para o iFood diretamente, não opera o maquininho de cartão. Ele fala com abstrações: "aceitar pagamento", "verificar estoque", "notificar cliente".

Na StockFlow: o use case ReceiveDelivery coordena: busca o pedido, muda o status para DELIVERED, atualiza o estoque de cada item, salva tudo. Ele não sabe se o banco é PostgreSQL — ele só sabe que existe um repositório que guarda dados.

🚗 A entrega e o caixa — equivale à INFRAESTRUTURA

São os detalhes técnicos concretos. O maquininho de cartão (Prisma/banco de dados), o app de delivery (NestJS/HTTP), o telefone (controller), o sistema de caixa (autenticação). Essas ferramentas podem mudar — trocar o iFood pelo Rappi, mudar de cartão para PIX — e a cozinha continua fazendo a mesma pizza.

Na StockFlow: o ProductPrismaRepository que conversa com o PostgreSQL, o ProductsController que recebe requisições HTTP, o AuthGuard que valida JWT. Se amanhã você trocar PostgreSQL por MongoDB, só muda esse pedaço — o domínio e os use cases continuam intactos.

Por que essa separação importa na prática?

Veja o que acontece sem separação de camadas — algo muito comum em projetos iniciantes:

// ❌ Tudo misturado num controller — difícil de testar, de manter e de evoluir
@Post('/purchase-orders/:id/deliver')
async deliver(@Param('id') id: string) {

  // Busca no banco (infraestrutura) misturada com...
  const order = await this.prisma.purchaseOrder.findUnique({ where: { id } })

  // ...regra de negócio (domínio) misturada com...
  if (order.status !== 'SENT') {
    throw new BadRequestException('Só pode entregar pedidos com status SENT')
  }

  // ...operação de banco (infraestrutura) misturada com...
  await this.prisma.purchaseOrder.update({
    where: { id },
    data: { status: 'DELIVERED' }
  })

  // ...outra regra de negócio (domínio)
  for (const item of order.items) {
    await this.prisma.stock.update({
      where: { productId: item.productId },
      data: { quantity: { increment: item.quantity } }
    })
  }
}

O problema desse código: para testar a regra "só pode entregar se status for SENT", você precisa subir o banco inteiro, rodar migrations, criar dados. Um teste simples vira um trabalho de infraestrutura.

Agora veja o mesmo cenário com separação de camadas:

// ✅ Domínio — regra isolada, testável sem nada externo
class PurchaseOrderEntity {
  markAsDelivered(): void {
    if (this.status !== 'SENT') {
      throw new Error('Só pode entregar pedidos com status SENT')
    }
    this.props.status = 'DELIVERED'
  }
}

// ✅ Aplicação — orquestra sem se preocupar com detalhes técnicos
class ReceiveDeliveryUseCase {
  async execute({ orderId }) {
    const order = await this.orderRepo.findById(orderId)  // não sabe se é Prisma ou não
    order.markAsDelivered()                               // regra do domínio
    for (const item of order.items) {
      const stock = await this.stockRepo.findByProductId(item.productId)
      stock.addQuantity(item.quantity)
      await this.stockRepo.update(stock)
    }
    await this.orderRepo.update(order)
  }
}

// ✅ Infraestrutura — detalhes técnicos isolados
class PurchaseOrderPrismaRepository {
  async findById(id: string) {
    const model = await this.prisma.purchaseOrder.findUnique({ where: { id } })
    return PurchaseOrderMapper.toEntity(model)  // converte modelo do banco → entidade
  }
}

A regra de ouro — direção das dependências

INFRAESTRUTURA  →  conhece  →  APLICAÇÃO  →  conhece  →  DOMÍNIO
    (NestJS)                  (Use Cases)               (Entidades)

DOMÍNIO nunca importa nada de Aplicação ou Infraestrutura
APLICAÇÃO nunca importa nada de Infraestrutura (NestJS, Prisma)
INFRAESTRUTURA pode importar de todos

Se você abrir um arquivo dentro de products/domain/ e ver um import from '@nestjs/...' ou import from '@prisma/...', algo está errado. O domínio é puro TypeScript — sem dependências externas.

Resumo: o que vai em cada camada

Camada Pasta O que fica aqui O que NUNCA fica aqui

Aplicação */application/ Use cases (CreateProduct, ReceiveDelivery, etc.), tipos de input/output NestJS decorators, Prisma, SQL, detalhes de HTTP

💡 Dica prática

Quando for escrever um código e não souber onde colocar, se pergunte: "Isso é uma regra do negócio ou um detalhe técnico?" Regra do negócio (ex: "não pode deletar fornecedor com pedidos ativos") → domínio. Detalhe técnico (ex: "salvar no PostgreSQL", "receber via HTTP POST") → infraestrutura. Coordenar os dois → aplicação.

Regras de Negócio

⚠️ Importante

Estas regras devem viver na camada de domínio (dentro das entidades e dos use cases), nunca nos controllers ou no banco de dados. Essa é a essência da Clean Architecture.

Cada regra abaixo tem o fluxo em desenho. A tabela no final é o checklist de onde implementar.

Status do pedido

O pedido nasce em DRAFT. Só pode ir para SENT (envio ainda fora desta API), ser cancelado, ou — depois de enviado — ser marcado como entregue. DELIVERED e CANCELLED são o fim: não voltam.

flowchart LR Inicio((inicio)) --> DRAFT DRAFT -->|"envio fora da API"| SENT DRAFT -->|"cancelar"| CANCELLED SENT -->|"receive-delivery"| DELIVERED SENT -->|"cancelar"| CANCELLED DELIVERED --> Fim((fim)) CANCELLED --> Fim

1. SKU único e imutável

O SKU identifica o produto. Na criação, se já existir outro igual, a API recusa (ConflictError). Depois de criado, não existe updateSku() — o código não muda.

flowchart TD A["POST /products"] --> B{"SKU ja existe?"} B -->|sim| C["ConflictError"] B -->|nao| D["Cria produto"] D --> E["SKU gravado"] E --> F["PUT /products"] F --> G["Altera nome, preco, etc"] G --> H["SKU permanece o mesmo"]

2. Preço de venda maior que o custo

Não dá para vender no prejuízo: price tem que ser maior que costPrice (valores em centavos). A validação mora na entidade Product, na criação e na atualização.

flowchart TD A["Criar ou atualizar produto"] --> B{"price maior que costPrice?"} B -->|nao| C["Erro de validacao"] B -->|sim| D["Produto aceito"]

3. CNPJ único

Cada fornecedor tem um CNPJ. O use case CreateSupplier consulta o repositório antes de gravar. Se o número já estiver em uso, lança ConflictError.

flowchart TD A["POST /suppliers"] --> B{"CNPJ ja existe?"} B -->|sim| C["ConflictError"] B -->|nao| D["Cria fornecedor"]

4. Não apagar fornecedor com pedido ativo

Pedido ativo = DRAFT ou SENT. Se o fornecedor ainda tiver um desses, DeleteSupplier recusa. Só apaga quando não há pedido em andamento (já entregue ou cancelado, ou nenhum pedido).

flowchart TD A["DELETE /suppliers/:id"] --> B{"Tem pedido DRAFT ou SENT?"} B -->|sim| C["Recusa a exclusao"] B -->|nao| D["Apaga o fornecedor"]

5. Estoque crítico

Estoque crítico é quando a quantidade atual fica abaixo do mínimo combinado: quantity < minQuantity. O getter na entidade Stock decide isso. A rota GET /stocks/critical lista esses casos para o lojista repor.

flowchart TD A["Estoque do produto"] --> B{"quantity menor que minQuantity?"} B -->|sim| C["Critico"] C --> D["GET /stocks/critical"] B -->|nao| E["Ok"]

6. Cancelar só em DRAFT ou SENT

Cancelar um pedido já entregue reescreveria a história do estoque. Por isso a entidade só aceita cancelamento em DRAFT ou SENT. Em DELIVERED ou CANCELLED, o use case lança ConflictError.

flowchart TD A["Cancelar pedido"] --> B{status} B -->|DRAFT| C["Vira CANCELLED"] B -->|SENT| C B -->|DELIVERED| D["ConflictError"] B -->|CANCELLED| D

7. Entrega sobe o estoque

POST /purchase-orders/:id/receive-delivery só roda se o pedido estiver SENT. Aí o status vira DELIVERED e cada item soma quantity no estoque daquele produto. Sem o passo SENT (ainda fora da API), essa rota não executa.

flowchart TD A["Pedido em SENT"] --> B["receive-delivery"] B --> C{"Status e SENT?"} C -->|nao| D["Recusa"] C -->|sim| E["Status vira DELIVERED"] E --> F["Para cada item"] F --> G["Estoque do produto += quantity"]

8. totalCost é calculado

O cliente não manda o total. A entidade PurchaseOrder soma quantity × unitCost de cada item. Se alguém passar um totalCost na criação, ele é ignorado e recalculado.

flowchart TD A["Itens do pedido"] --> B["item: quantity x unitCost"] B --> C["Soma todos os itens"] C --> D["totalCost gravado"]

Seção 2 — Criando o Projeto

📚 O que o curso ensina

O curso instala a CLI do NestJS, cria o projeto, configura variáveis de ambiente com um módulo dedicado (EnvConfigModule) e escreve testes unitários para o serviço de configuração. Isso garante que toda a aplicação lê configurações de um único lugar centralizado.

🔗 Na StockFlow API

Vamos fazer exatamente a mesma coisa, mas nossas variáveis de ambiente incluirão configurações de banco, Redis (se quiser cache), JWT e AWS.

Passo 1 — Instalar NestJS CLI e criar projeto

A CLI (Command Line Interface) do NestJS é uma ferramenta que roda no terminal e gera a estrutura inicial do projeto automaticamente. Sem ela, você teria que criar todos os arquivos de configuração manualmente. Com ela, um único comando já te dá um projeto funcional com TypeScript configurado, testes prontos e estrutura de pastas básica.

O --package-manager pnpm diz para a CLI já configurar o projeto para usar pnpm em vez de npm — evita que ela instale as dependências com npm e você precise reinstalar com pnpm depois.

# Instalar CLI global
pnpm add -g @nestjs/cli

# Criar projeto (selecionar pnpm quando perguntar o package manager)
nest new stockflow-api --package-manager pnpm

cd stockflow-api

Passo 2 — Instalar dependências e criar o .env

Toda aplicação precisa de configurações que mudam dependendo do ambiente — em desenvolvimento você usa um banco local, em produção você usa o banco da AWS. Essas configurações nunca devem estar no código (senão você commitaria sua senha do banco no GitHub). A solução é o arquivo .env: um arquivo local que cada ambiente tem com seus próprios valores.

Instalamos três pacotes aqui:

  • @nestjs/config — módulo do NestJS que lê o arquivo .env e disponibiliza os valores para a aplicação
  • zod — biblioteca de validação que usaremos em toda a aplicação (variáveis de ambiente, DTOs, entidades)
  • class-transformer — transforma objetos JavaScript simples em instâncias de classes e vice-versa (usado nos Presenters)

O arquivo .env.example que você deve criar junto é um "template" — ele documenta quais variáveis o projeto precisa sem expor os valores reais. Quando outro desenvolvedor clonar o projeto, ele sabe exatamente o que precisa configurar.

# Zod para toda validação do projeto (env, DTOs, inputs)
pnpm add @nestjs/config zod class-transformer
pnpm add -D @types/node

Criar o arquivo .env na raiz:

# .env

Passo 4 — Módulo de configuração de ambiente

Agora vamos criar a forma correta de ler e usar as variáveis do .env dentro da aplicação. Você pode se perguntar: "por que não simplesmente usar process.env.DATABASE_URL diretamente no código?"

O problema é que process.env retorna string | undefined para qualquer variável — o TypeScript não tem como saber quais existem nem quais são seus tipos. Se você esquecer de configurar uma variável, o erro só aparece em tempo de execução, quando a aplicação já está rodando.

A solução é criar um serviço de configuração que:

  • Valida na inicialização: se uma variável obrigatória estiver faltando, a aplicação nem sobe — você descobre o erro antes de qualquer requisição chegar
  • Centraliza o acesso: todo o código que precisar de configuração chama envConfigService.getJwtSecret() em vez de espalhar process.env.JWT_SECRET por vários arquivos
  • Tipagem correta: getPort() retorna number, não string — sem conversões manuais espalhadas pelo código

Criamos três arquivos que trabalham juntos:

  • Interface (env-config.interface.ts) — define o contrato: quais métodos o serviço de configuração deve ter. Isso permite trocar a implementação no futuro sem quebrar nada
  • Service (env-config.service.ts) — a implementação concreta que lê as variáveis usando o ConfigService do NestJS
  • Module (env-config.module.ts) — registra o service no NestJS e configura o Zod para validar as variáveis assim que a aplicação iniciar

import { Module } from '@nestjs/common'
import { ConfigModule } from '@nestjs/config'
import { EnvConfigService } from './env-config.service'
import { z } from 'zod'

// Schema Zod para validação das variáveis de ambiente
const envSchema = z.object({
  PORT: z.coerce.number().default(3000),
  NODE_ENV: z.enum(['development', 'production', 'test']).default('development'),
  DATABASE_URL: z.string().url(),
  JWT_SECRET: z.string().min(32),
  JWT_EXPIRES_IN: z.string().default('15m'),
})

// Tipo inferido automaticamente pelo Zod — sem duplicar interfaces
export type EnvVars = z.infer<typeof envSchema>

@Module({
  imports: [
    ConfigModule.forRoot({
      // validate substitui o validationSchema do Joi
      validate: (config: Record<string, unknown>) => {
        const parsed = envSchema.safeParse(config)

        if (!parsed.success) {
          const errors = parsed.error.format()
          throw new Error(`Invalid environment variables: ${JSON.stringify(errors)}`)
        }

        return parsed.data
      },
    }),
  ],
  providers: [EnvConfigService],
  exports: [EnvConfigService],
})
export class EnvConfigModule {}

Seção 3 — Implementando Entidades

📚 O que o curso ensina

O curso cria a entidade User com props tipadas, getters, métodos de atualização, e uma classe base abstrata Entity com ID gerado por UUID. Também cria um helper UserDataBuilder para facilitar testes. O padrão é que toda entidade estende Entity e recebe suas props no construtor.

🔗 Na StockFlow API

Vamos criar a mesma estrutura, mas com Product como entidade principal (equivalente ao User do curso). Depois, você replicará o padrão para Supplier, Stock e PurchaseOrder.

Passo 1 — Classe base Entity

Toda entidade do sistema (Product, Supplier, Stock, PurchaseOrder) tem algo em comum: precisa de um identificador único. Em vez de repetir esse código em cada entidade, criamos uma classe base abstrata que todas elas herdam.

Usamos UUID (Universally Unique Identifier) como ID em vez de um número auto-incremento do banco. Por quê? Porque o UUID é gerado na camada de domínio, sem precisar falar com o banco. Isso significa que você pode criar uma entidade, fazer validações e testes nela, sem que o banco de dados precise existir ainda. O ID do banco auto-incremento só existe depois de salvar — o UUID existe desde o momento da criação da entidade.

O parâmetro opcional id? no construtor serve para quando você está reconstruindo uma entidade que já existia no banco — nesse caso, você passa o ID que já estava salvo em vez de gerar um novo.

src/shared/domain/entities/entity.ts

import { v4 as uuidv4 } from 'uuid'

export abstract class Entity<Props> {
  public readonly _id: string
  public readonly props: Props

  constructor(props: Props, id?: string) {
    this.props = props
    this._id = id ?? uuidv4()
  }

  get id(): string {
    return this._id
  }
}

Passo 2 — Entidade Product

Aqui criamos a entidade Product — e é importante entender o que uma "entidade" é no contexto do DDD. Uma entidade não é apenas um objeto com dados. É um objeto que tem identidade única e que sabe se comportar de acordo com as regras do negócio.

Repare em algumas decisões de design:

  • Props em centavos (price: number): guardamos preços como inteiros em centavos (1990 = R$19,90) para evitar problemas com ponto flutuante. R$19.90 em float pode virar 19.899999999 em operações matemáticas.
  • Getters em vez de acesso direto: a entidade expõe product.name como getter, não como propriedade pública direta. Isso permite que no futuro você adicione lógica dentro do getter sem quebrar quem usa.
  • Não existe updateSku(): isso é intencional. SKU é imutável após criação — é uma regra de negócio. A ausência do método é a regra.
  • Regra no updatePrice(): o método verifica se o novo preço é maior que o custo. Essa verificação mora aqui, não no controller, não no use case — ela está na entidade porque é uma invariante do negócio que deve sempre ser respeitada.

src/products/domain/entities/product.entity.ts

import { Entity } from '@/shared/domain/entities/entity'

export interface ProductProps {
  name: string
  description: string
  sku: string
  price: number           // em centavos (1999 = R$ 19,99)
  costPrice: number       // em centavos
  category: string
  supplierId: string
  isActive: boolean
  createdAt?: Date
  updatedAt?: Date
}

export class ProductEntity extends Entity<ProductProps> {
  constructor(props: ProductProps, id?: string) {
    super(
      {
        ...props,
        isActive: props.isActive ?? true,
        createdAt: props.createdAt ?? new Date(),
        updatedAt: props.updatedAt ?? new Date(),
      },
      id,
    )
  }

  // ── Getters ──
  get name(): string {
    return this.props.name
  }

  get description(): string {
    return this.props.description
  }

  get sku(): string {
    return this.props.sku
  }

  get price(): number {
    return this.props.price
  }

  get costPrice(): number {
    return this.props.costPrice
  }

  get category(): string {
    return this.props.category
  }

  get supplierId(): string {
    return this.props.supplierId
  }

  get isActive(): boolean {
    return this.props.isActive
  }

  get createdAt(): Date {
    return this.props.createdAt
  }

  get updatedAt(): Date {
    return this.props.updatedAt
  }

  // ── Regra de negócio: margem de lucro ──
  get profitMargin(): number {
    if (this.costPrice === 0) return 0
    return ((this.price - this.costPrice) / this.costPrice) * 100
  }

  // ── Métodos de atualização ──
  updateName(value: string): void {
    this.props.name = value
    this.props.updatedAt = new Date()
  }

  updateDescription(value: string): void {
    this.props.description = value
    this.props.updatedAt = new Date()
  }

  updatePrice(value: number): void {
    // Regra: preço de venda deve ser maior que custo
    if (value <= this.costPrice) {
      throw new Error('Price must be greater than cost price')
    }
    this.props.price = value
    this.props.updatedAt = new Date()
  }

  updateCostPrice(value: number): void {
    this.props.costPrice = value
    this.props.updatedAt = new Date()
  }

  deactivate(): void {
    this.props.isActive = false
    this.props.updatedAt = new Date()
  }

  activate(): void {
    this.props.isActive = true
    this.props.updatedAt = new Date()
  }

  // NOTA: não existe updateSku() — SKU é imutável após criação
}

Passo 3 — DataBuilder para testes

Ao escrever testes, você vai precisar criar instâncias de ProductEntity repetidamente. Sem o DataBuilder, cada teste teria que preencher todos os campos manualmente — nome, sku, preço, custo, categoria, supplierId... Se a entidade tiver 10 campos, são 10 linhas repetidas em cada teste.

O DataBuilder resolve isso gerando dados válidos e aleatórios (usando a lib faker) para todos os campos. A grande vantagem é o parâmetro parcial (Partial<ProductProps>): você só passa os campos que importam para aquele teste específico, e o resto é preenchido automaticamente.

Por exemplo: se você quer testar a regra "preço deve ser maior que custo", você passa só price e costPrice — o resto do produto não importa para esse teste.

Seção 4 — Validação dos Dados

📚 O que o curso ensina

O curso implementa validação na camada de domínio usando class-validator. Cria uma interface de validação (ValidatorFieldsInterface), uma classe concreta que usa decorators do class-validator, e depois integra essa validação dentro da entidade User. Os testes cobrem cada propriedade individualmente, incluindo testes de integração entre a entidade e o validador.

🔗 Na StockFlow API

Mesma abordagem, mas as validações são diferentes: SKU precisa ter formato específico, price e costPrice devem ser inteiros positivos (centavos), a relação entre eles deve ser validada, etc.

Passo 1 — Interface do validador

Antes de implementar a validação, definimos uma interface que descreve como qualquer validador deve se comportar. Isso segue o mesmo princípio do repositório: o domínio declara o contrato, a implementação concreta pode mudar.

A interface tem três partes: errors (os erros encontrados, organizados por campo), validatedData (os dados válidos após a validação), e validate() (o método que executa a validação e retorna true ou false). Qualquer classe que implemente essa interface pode ser usada como validador — seja com Zod, seja com qualquer outra lib no futuro.

src/shared/domain/validators/validator-fields.interface.ts

export type FieldsErrors = {
  [field: string]: string[]
}

export interface ValidatorFieldsInterface<ValidatedProps> {
  errors: FieldsErrors
  validatedData: ValidatedProps
  validate(data: any): boolean
}

Passo 2 — Implementação com Zod

Aqui criamos a implementação concreta da interface — a classe que de fato executa a validação usando Zod. Ela fica em shared/domain/ porque todos os módulos vão reutilizá-la — Product, Supplier, Stock e PurchaseOrder usarão essa mesma classe base, só passando schemas Zod diferentes.

O método safeParse do Zod é diferente de parse: em vez de lançar uma exceção quando encontra erro, ele retorna um objeto com success: true/false. Isso nos dá controle para formatar os erros do jeito que queremos antes de jogar para quem chamou.

src/shared/domain/validators/zod-validator-fields.ts

import { ZodSchema, ZodError } from 'zod'
import { FieldsErrors, ValidatorFieldsInterface } from './validator-fields.interface'

export class ZodValidatorFields<ValidatedProps>
  implements ValidatorFieldsInterface<ValidatedProps>
{
  errors: FieldsErrors = {}
  validatedData: ValidatedProps = null

  constructor(private schema: ZodSchema) {}

  validate(data: any): boolean {
    const result = this.schema.safeParse(data)

    if (!result.success) {
      this.errors = this.formatErrors(result.error)
      return false
    }

    this.validatedData = result.data as ValidatedProps
    return true
  }

  private formatErrors(error: ZodError): FieldsErrors {
    const formatted: FieldsErrors = {}

    for (const issue of error.issues) {
      const field = issue.path.join('.')
      if (!formatted[field]) formatted[field] = []
      formatted[field].push(issue.message)
    }

    return formatted
  }
}

Passo 3 — Schema e Validador do Product com Zod

Agora criamos o schema específico do Product — as regras de validação que definem o que é um produto válido. Repare na grande vantagem do Zod aqui: export type ProductValidated = z.infer<typeof productSchema> gera o tipo TypeScript automaticamente a partir das regras do schema. Você define as regras uma vez e o TypeScript já sabe os tipos de todos os campos — sem repetir interfaces.

Cada regra tem uma mensagem de erro personalizada (segundo argumento de cada método). Isso significa que quando a validação falhar, o erro vai dizer exatamente o que está errado — "SKU must be 3-20 uppercase alphanumeric characters" é muito mais útil do que "invalid input".

  name: z
    .string()
    .min(1, 'Name is required')
    .max(255, 'Name must be less than 255 characters'),

💡 Zod vs class-validator — por que trocamos

O curso usa class-validator (decorators + classes). Na POC usamos Zod porque:

  • Type inference: z.infer<typeof schema> gera o tipo automaticamente — com class-validator você precisa definir a interface separadamente
  • Zero classes/decorators: schemas são objetos simples, mais fáceis de compor e reutilizar
  • Ecossistema TypeScript-first: Zod foi construído para TypeScript, class-validator vem do mundo JavaScript
  • Mesma lib em todas as camadas: env config, DTOs, domínio — tudo com Zod

O padrão do curso (ValidatorFieldsInterface → implementação concreta → Factory) continua o mesmo — só trocamos o motor interno de class-validator para Zod.

Seção 5 — Repository Pattern

📚 O que o curso ensina

O curso cria uma abstração de repositório (interface) na camada de domínio, depois implementa um repositório InMemory para testes. Inclui busca personalizada com filtro, ordenação e paginação. O repositório InMemory simula o banco de dados na memória — usado nos testes unitários dos use cases.

Passo 1 — Interface base do repositório

O Repository Pattern resolve um problema de dependência: o domínio precisa salvar e buscar dados, mas não pode depender do Prisma (infraestrutura). A solução é o domínio declarar o que precisa através de uma interface — sem saber como vai ser implementado.

Pense assim: a interface é como um contrato de serviço. O domínio diz "preciso de alguém que saiba inserir, buscar por ID, listar todos, atualizar e deletar". Quem vai cumprir esse contrato? Pode ser o Prisma em produção, ou um array em memória nos testes. A interface não se importa.

O SearchableRepositoryInterface estende o básico com um método search que aceita filtros, ordenação e paginação — usado nos endpoints de listagem com query params.

export interface RepositoryInterface<E> {
  insert(entity: E): Promise<void>
  findById(id: string): Promise<E>
  findAll(): Promise<E[]>
  update(entity: E): Promise<void>
  delete(id: string): Promise<void>
}

// Para repositórios com busca paginada
export interface SearchParams {
  page?: number
  perPage?: number
  sort?: string | null
  sortDir?: 'asc' | 'desc' | null
  filter?: string | null
}

export interface SearchResult<E> {
  items: E[]
  total: number
  currentPage: number
  perPage: number
  lastPage: number
}

export interface SearchableRepositoryInterface<E>
  extends RepositoryInterface<E> {
  search(params: SearchParams): Promise<SearchResult<E>>
}

Passo 2 — Interface do repositório de Product

Além dos métodos genéricos de CRUD, o repositório de Product precisa de métodos específicos do negócio — como findBySku e skuExists. Esses métodos são declarados aqui, na interface de domínio, porque fazem parte do contrato que qualquer implementação (Prisma, InMemory) deve cumprir.

Nota importante: a interface fica em domain/repositories/ (domínio), mas as implementações (ProductPrismaRepository, ProductInMemoryRepository) ficam em infrastructure/. O domínio nunca vai saber como esses métodos são implementados.

Passo 3 — Repositório InMemory base

Este é um dos arquivos mais importantes para os testes da aplicação. O InMemoryRepository implementa o contrato do repositório usando um simples array em memória (items: E[] = []) em vez do banco de dados.

Por que isso é valioso? Porque nos testes unitários dos use cases, você passa um ProductInMemoryRepository em vez do ProductPrismaRepository. Os testes rodam em milissegundos, sem precisar de Docker, sem banco, sem migrations. O use case não sabe a diferença — ele só fala com a interface, e ambas as implementações cumprem o mesmo contrato.

O array items é público para facilitar verificações nos testes: você consegue inspecionar diretamente o que foi inserido com expect(repository.items).toHaveLength(1).

src/shared/domain/repositories/in-memory.repository.ts

import { Entity } from '../entities/entity'
import { RepositoryInterface } from './repository-contracts'
import { NotFoundError } from '../errors/not-found-error'

export abstract class InMemoryRepository<E extends Entity<any>>
  implements RepositoryInterface<E>
{
  items: E[] = []

  async insert(entity: E): Promise<void> {
    this.items.push(entity)
  }

  async findById(id: string): Promise<E> {
    const entity = this.items.find(item => item.id === id)
    if (!entity) {
      throw new NotFoundError(`Entity with id ${id} not found`)
    }
    return entity
  }

  async findAll(): Promise<E[]> {
    return this.items
  }

  async update(entity: E): Promise<void> {
    const index = this.items.findIndex(item => item.id === entity.id)
    if (index === -1) {
      throw new NotFoundError(`Entity with id ${entity.id} not found`)
    }
    this.items[index] = entity
  }

  async delete(id: string): Promise<void> {
    const index = this.items.findIndex(item => item.id === id)
    if (index === -1) {
      throw new NotFoundError(`Entity with id ${id} not found`)
    }
    this.items.splice(index, 1)
  }
}

CreateProduct — o use case mais importante

Use cases são o coração da camada de aplicação. Cada um representa uma ação que o sistema pode fazer — como criar um produto. Repare na estrutura do arquivo: ele usa um namespace para agrupar o Input, o Output e a classe UseCase juntos. Isso mantém tudo relacionado ao mesmo caso de uso em um lugar só.

Pontos importantes deste use case:

  • Recebe a interface, não a implementação: o construtor recebe ProductRepository (interface), não ProductPrismaRepository. Isso é injeção de dependência — quem cria o use case decide qual implementação passar.
  • Sequência de operações: primeiro verifica o SKU (regra de unicidade), depois verifica o preço, depois cria a entidade (que roda suas próprias validações Zod), depois persiste. Se qualquer passo falhar, os seguintes não executam.
  • Output é um objeto simples: não retornamos a entidade diretamente. Retornamos um objeto com apenas os campos que fazem sentido expor. Isso desacopla o que o caso de uso entrega do que a entidade contém internamente.

src/products/application/usecases/create-product.usecase.ts

import { UseCase } from '@/shared/application/usecases/use-case'
import { ProductEntity } from '@/products/domain/entities/product.entity'
import { ProductRepository } from '@/products/domain/repositories/product.repository'
import { ConflictError } from '@/shared/domain/errors/conflict-error'

export namespace CreateProductUseCase {
  export interface Input {
    name: string
    description: string
    sku: string
    price: number
    costPrice: number
    category: string
    supplierId: string
  }

  export interface Output {
    id: string
    name: string
    sku: string
    price: number
    costPrice: number
    category: string
    supplierId: string
    isActive: boolean
    createdAt: Date
  }

  export class UseCase implements UseCase<Input, Output> {
    constructor(private productRepository: ProductRepository) {}

    async execute(input: Input): Promise<Output> {
      // Regra: SKU é único
      const skuExists = await this.productRepository.skuExists(input.sku)
      if (skuExists) {
        throw new ConflictError(`SKU ${input.sku} already exists`)
      }

      // Regra: preço de venda > preço de custo
      if (input.price <= input.costPrice) {
        throw new Error('Price must be greater than cost price')
      }

      // Cria a entidade (validações do domínio rodam aqui)
      const entity = new ProductEntity(input)

      // Persiste via repositório
      await this.productRepository.insert(entity)

      // Retorna o output mapeado
      return {
        id: entity.id,
        name: entity.name,
        sku: entity.sku,
        price: entity.price,
        costPrice: entity.costPrice,
        category: entity.category,
        supplierId: entity.supplierId,
        isActive: entity.isActive,
        createdAt: entity.createdAt,
      }
    }
  }
}

ReceiveDelivery — o use case mais complexo da POC

src/purchase-orders/application/usecases/receive-delivery.usecase.ts

import { UseCase } from '@/shared/application/usecases/use-case'
import { PurchaseOrderRepository } from '../../domain/repositories/purchase-order.repository'
import { StockRepository } from '@/stock/domain/repositories/stock.repository'

export namespace ReceiveDeliveryUseCase {
  export interface Input {
    purchaseOrderId: string
  }

  export interface Output {
    id: string
    status: string
    updatedStockItems: Array<{ productId: string; newQuantity: number }>
  }

  export class UseCase implements UseCase<Input, Output> {
    constructor(
      private purchaseOrderRepo: PurchaseOrderRepository,
      private stockRepo: StockRepository,
    ) {}

    async execute(input: Input): Promise<Output> {
      // 1. Buscar pedido de compra
      const order = await this.purchaseOrderRepo.findById(input.purchaseOrderId)

      // 2. Mudar status para DELIVERED (entidade valida transição)
      order.markAsDelivered()

      // 3. Atualizar estoque de cada item
      const updatedStockItems = []

      for (const item of order.items) {
        const stock = await this.stockRepo.findByProductId(item.productId)
        stock.addQuantity(item.quantity)
        await this.stockRepo.update(stock)

        updatedStockItems.push({
          productId: item.productId,
          newQuantity: stock.quantity,
        })
      }

      // 4. Persistir pedido atualizado
      await this.purchaseOrderRepo.update(order)

      return {
        id: order.id,
        status: order.status,
        updatedStockItems,
      }
    }
  }
}

import { PipeTransform, BadRequestException } from '@nestjs/common'
import { ZodSchema } from 'zod'

export class ZodValidationPipe implements PipeTransform {
  constructor(private schema: ZodSchema) {}

  transform(value: unknown) {
    const result = this.schema.safeParse(value)

    if (!result.success) {
      const errors = result.error.issues.map((issue) => ({
        field: issue.path.join('.'),
        message: issue.message,
      }))
      throw new BadRequestException({ message: 'Validation failed', errors })
    }

    return result.data
  }
}

📚 O que o curso ensina

ModelMapper — traduz Prisma ↔ Domínio

Aqui temos um problema interessante: o Prisma retorna objetos do tipo Product (modelo do banco), mas o use case espera receber um ProductEntity (entidade do domínio). São dois objetos diferentes — o modelo do Prisma é um objeto plano com dados do banco, a entidade tem comportamentos e validações.

O ModelMapper é o tradutor entre esses dois mundos. Ele pega um objeto Prisma e constrói uma ProductEntity a partir dele. Note o detalhe crítico: passamos o model.id como segundo argumento — isso diz para a entidade "use este ID que já existe no banco" em vez de gerar um novo UUID.

Esse arquivo fica na camada de infraestrutura porque ele conhece os dois lados: sabe o formato do Prisma e sabe construir a entidade do domínio.

src/products/infrastructure/database/prisma/product-model.mapper.ts

import { Product as ProductModel } from '@prisma/client'
import { ProductEntity } from '@/products/domain/entities/product.entity'

export class ProductModelMapper {
  // Prisma Model → Domain Entity
  static toEntity(model: ProductModel): ProductEntity {
    return new ProductEntity(
      {
        name: model.name,
        description: model.description ?? '',
        sku: model.sku,
        price: model.price,
        costPrice: model.costPrice,
        category: model.category,
        supplierId: model.supplierId,
        isActive: model.isActive,
        createdAt: model.createdAt,
        updatedAt: model.updatedAt,
      },
      model.id,  // passa o ID existente, não gera novo
    )
  }
}

Repositório Prisma de Product

Esta é a implementação concreta do contrato ProductRepository que usa o Prisma para falar com o PostgreSQL. Repare que a classe implementa a interface (implements ProductRepository) — o TypeScript vai reclamar se você esquecer de implementar algum método do contrato.

Compare o findById aqui com o mesmo método no InMemory: o comportamento é idêntico do ponto de vista do use case (retorna uma entidade ou lança NotFoundError), mas a implementação é completamente diferente. É exatamente isso que o padrão Repository permite — trocar a implementação sem mudar quem usa.

src/products/infrastructure/database/prisma/product-prisma.repository.ts

import { PrismaService } from '@/shared/infrastructure/database/prisma/prisma.service'
import { ProductRepository } from '@/products/domain/repositories/product.repository'
import { ProductEntity } from '@/products/domain/entities/product.entity'
import { ProductModelMapper } from './product-model.mapper'
import { NotFoundError } from '@/shared/domain/errors/not-found-error'

export class ProductPrismaRepository implements ProductRepository {
  constructor(private prisma: PrismaService) {}

  async insert(entity: ProductEntity): Promise<void> {
    await this.prisma.product.create({
      data: {
        id: entity.id,
        name: entity.name,
        description: entity.description,
        sku: entity.sku,
        price: entity.price,
        costPrice: entity.costPrice,
        category: entity.category,
        supplierId: entity.supplierId,
        isActive: entity.isActive,
        createdAt: entity.createdAt,
      },
    })
  }

  async findById(id: string): Promise<ProductEntity> {
    const model = await this.prisma.product.findUnique({
      where: { id },
    })

    if (!model) {
      throw new NotFoundError(`Product with id ${id} not found`)
    }

    return ProductModelMapper.toEntity(model)
  }

  async findBySku(sku: string): Promise<ProductEntity> {
    const model = await this.prisma.product.findUnique({
      where: { sku },
    })

    if (!model) {
      throw new NotFoundError(`Product with SKU ${sku} not found`)
    }

    return ProductModelMapper.toEntity(model)
  }

  async skuExists(sku: string): Promise<boolean> {
    const count = await this.prisma.product.count({
      where: { sku },
    })
    return count > 0
  }

  async findBySupplierId(supplierId: string): Promise<ProductEntity[]> {
    const models = await this.prisma.product.findMany({
      where: { supplierId },
    })
    return models.map(ProductModelMapper.toEntity)
  }

  async findAll(): Promise<ProductEntity[]> {
    const models = await this.prisma.product.findMany()
    return models.map(ProductModelMapper.toEntity)
  }

  async update(entity: ProductEntity): Promise<void> {
    await this.prisma.product.update({
      where: { id: entity.id },
      data: {
        name: entity.name,
        description: entity.description,
        price: entity.price,
        costPrice: entity.costPrice,
        category: entity.category,
        isActive: entity.isActive,
        updatedAt: entity.updatedAt,
      },
    })
  }

  async delete(id: string): Promise<void> {
    await this.prisma.product.delete({
      where: { id },
    })
  }

  async search(params) {
    const { page = 1, perPage = 15, sort, sortDir, filter } = params

    const where = filter
      ? { name: { contains: filter, mode: 'insensitive' as const } }
      : {}

    const [items, total] = await Promise.all([
      this.prisma.product.findMany({
        where,
        orderBy: sort ? { [sort]: sortDir ?? 'asc' } : { createdAt: 'desc' },
        skip: (page - 1) * perPage,
        take: perPage,
      }),
      this.prisma.product.count({ where }),
    ])

    return {
      items: items.map(ProductModelMapper.toEntity),
      total,
      currentPage: page,
      perPage,
      lastPage: Math.ceil(total / perPage),
    }
  }
}

📚 O que o curso ensina

⚠️ Atenção — nunca rode os testes contra o banco de desenvolvimento

O cleanDatabase() apaga todas as tabelas antes de cada teste. Se rodar contra o banco de dev (stockflow_db), você perde todos os seus dados de seed. A solução é um banco separado exclusivo para testes.

O setup-prisma-tests.ts chama config({ path: '.env.test', override: true }) no início do arquivo. Isso garante que qualquer DATABASE_URL já definida no ambiente seja substituída pela URL do banco de teste — independente de onde os testes são executados.

package.json (trecho)

"migrate:test": "DOTENV_FILE=.env.test npx prisma db push"
💡 Por que usar dotenv-cli?

A engine do Prisma CLI carrega o prisma.config.ts com seu próprio mecanismo, onde qualquer import 'dotenv/config' sobrescreve variáveis passadas externamente. A solução é fazer o próprio prisma.config.ts decidir qual .env carregar com base em DOTENV_FILE. Por padrão carrega .env; quando DOTENV_FILE=.env.test é setado antes do comando, o Prisma conecta ao banco de teste. O --skip-generate evita regenerar o client desnecessariamente.

Repita este comando sempre que criar novas migrations.

// Order respects FK constraints: items → orders → stocks → products → suppliers

  await prisma.purchaseOrder.deleteMany()
  await prisma.stock.deleteMany()

Seção 12 — Testes End-to-End (E2E)

📚 O que o curso ensina

O curso implementa testes e2e com Supertest — requests HTTP reais contra a aplicação NestJS completa. Antes disso, configura interceptor (WrapperData), exception filters (ConflictErrorFilter, NotFoundErrorFilter) e o applyGlobalConfig para a app de teste se comportar igual à de produção.

💡 E2E vs integração vs unitário

Os três testam camadas diferentes. Confundir isso gera testes frágeis ou que não pegam o bug certo.

TipoO que sobeO que validaExemplo
Unitário Nada de HTTP, nada de banco. Repositório in-memory. Regra de negócio isolada. CreateProductUseCase lança ConflictError se o SKU já existe.
Integração Banco real. Sem HTTP. Prisma persiste e lê certo. ProductPrismaRepository.insert grava a linha na tabela.
E2E App NestJS + HTTP + banco real. Rota, pipe, use case, presenter, filter — o caminho inteiro. POST /products devolve 201 e body.data.sku.

E2E usa o mesmo banco de teste da seção 10/11 (stockflow_test_db + cleanDatabase()). Docker precisa estar no ar e pnpm migrate:test já ter rodado.

Passo 1 — Interceptor WrapperData

O curso envolve toda resposta de sucesso em { data: ... }. Sem isso, o teste espera res.body.data.id e recebe res.body.id.

src/shared/infrastructure/interceptors/wrapper-data.interceptor.ts

import { CallHandler, ExecutionContext, Injectable, NestInterceptor } from '@nestjs/common'
import { Observable, map } from 'rxjs'

@Injectable()
export class WrapperDataInterceptor implements NestInterceptor {
  intercept(_context: ExecutionContext, next: CallHandler): Observable<unknown> {
    return next.handle().pipe(
      map((body) => {
        if (!body || typeof body !== 'object') return body
        if ('accessToken' in body) return body // login não vai dentro de data
        return { data: body }
      }),
    )
  }
}

Passo 2 — Exception filters

Erros de domínio (NotFoundError, ConflictError) não são HTTP por padrão. Sem filter, o Nest devolve 500. Os filters traduzem:

Erro de domínioHTTPQuando acontece
NotFoundError404GET /products/:id com UUID inexistente
ConflictError409POST /products com SKU que já existe
BadRequestException (Zod)400Body inválido — o ZodValidationPipe já lança isso

src/shared/infrastructure/exception-filters/not-found-error.filter.ts

import { ArgumentsHost, Catch, ExceptionFilter } from '@nestjs/common'
import { Response } from 'express'
import { NotFoundError } from '@/shared/domain/errors'

@Catch(NotFoundError)
export class NotFoundErrorFilter implements ExceptionFilter {
  catch(exception: NotFoundError, host: ArgumentsHost) {
    const response = host.switchToHttp().getResponse<Response>()
    response.status(404).json({
      statusCode: 404,
      error: 'Not Found',
      message: exception.message,
    })
  }
}

O ConflictErrorFilter é o mesmo padrão com status 409 e @Catch(ConflictError).

💡 Curso vs StockFlow na validação

O curso usa ValidationPipe do Nest (class-validator) e costuma esperar 422. A StockFlow valida com Zod via ZodValidationPipe, que lança BadRequestException → 400. Nos testes E2E, assert 400 para body inválido — não 422.

Passo 3 — applyGlobalConfig

Pipes, filters e interceptors precisam estar na app de produção e na app do teste. Se o teste não aplicar a mesma config, o E2E passa um comportamento que o servidor real não tem.

Seção 13 — Presenters

📚 O que o curso ensina

O curso cria classes Presenter para formatar a resposta HTTP. O UserPresenter escolhe quais campos o cliente recebe, o PaginationPresenter formata metadados de paginação, e o CollectionPresenter junta os dois para listagens.

💡 Por que o presenter existe

O use case devolve um objeto de domínio (output). O controller não devolve esse objeto cru. Ele passa o output para um presenter, que monta exatamente o JSON da API.

Isso permite esconder campos internos, formatar valores (centavos → reais, Date → ISO) e mudar a resposta sem tocar no use case.

Cliente HTTP
    ↑ JSON
Controller  →  new ProductPresenter(output)
    ↑ output
Use Case    →  entidade / dados de negócio
    ↑
Repository  →  banco

Passo 1 — Tipos locais (sem acoplar a um use case)

Passo 2 — Presenter de um item

É uma classe, não um type: o NestJS serializa instâncias de classe como JSON automaticamente. Os campos declarados aqui são exatamente o que o cliente recebe. Para esconder costPrice, basta removê-lo daqui — sem mudar o use case.

export class ProductPresenter {

Seção 14 — Autenticação com Auth0

📚 O que o curso ensina

O curso gera e valida JWT na própria API (AuthService + bcrypt + POST /login). Na StockFlow isso sai: MFA, recuperação de senha e login social são trabalho demais para um POC — e fáceis de errar. Quem assume identidade é o Auth0 (Authorization Server). O NestJS é só o resource server: valida o access token. Fonte: Auth0 APIs.

🔗 Por que Auth0 (e não JWT caseiro nem Clerk)

A StockFlow é uma API testada no Postman e no Swagger. O Auth0 registra isso como API (audience) e emite JWT RS256. O Clerk brilha em Next.js; aqui o backend só precisa validar Bearer via JWKS, como no backend quickstart e no guia NestJS da Auth0.

Isso só vale para login de usuário. Token M2M não passa por MFA nem por tela de senha.

💡 O que é JWKS

JSON Web Key Set: endpoint público com as chaves que validam a assinatura. Você não guarda o secret de assinatura no .env. Se o Auth0 rotacionar a chave, o jwks-rsa busca de novo (com cache).

export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor(envConfig: EnvConfigService) {
    const domain = envConfig.getAuth0Domain()
    const issuer = `https://${domain}/`

    super({
      secretOrKeyProvider: passportJwtSecret({
        cache: true,
        rateLimit: true,
        jwksRequestsPerMinute: 5,
        jwksUri: `https://${domain}/.well-known/jwks.json`,
      }),
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      audience: envConfig.getAuth0Audience(),
      issuer,
      algorithms: ['RS256'],
    })
  }

  validate(payload: Auth0JwtPayload): Auth0JwtPayload {
    return payload
  }
}

validate só roda depois que a assinatura passou. O retorno vira request.user. Em token de usuário, sub é o id no Auth0. Em token M2M, sub é {client_id}@clients — não é um admin humano.

Escopos (scope) são o próximo passo oficial se a API tiver permissões por endpoint. Neste POC um token válido para a audience já libera as rotas.

const getAccessToken = async (): Promise<string> => {
  const res = await fetch(`https://${process.env.AUTH0_DOMAIN}/oauth/token`, {
    method: 'POST',
    headers: { 'content-type': 'application/x-www-form-urlencoded' },
    body: new URLSearchParams({
      grant_type: 'client_credentials',
      client_id: process.env.AUTH0_CLIENT_ID ?? '',
      client_secret: process.env.AUTH0_CLIENT_SECRET ?? '',
      audience: process.env.AUTH0_AUDIENCE ?? '',
    }),
  })
  const json = (await res.json()) as { access_token?: string; error?: string }

  if (!res.ok || !json.access_token) {
    throw new Error(`Auth0 token failed: ${json.error ?? res.status}`)
  }

  return json.access_token
}

const auth = (token: string) => ({ Authorization: `Bearer ${token}` })

const token = await getAccessToken()
await request(server).get('/products').set(auth(token)).expect(200)
await request(server).get('/products').expect(401)

AUTH0_CLIENT_ID e AUTH0_CLIENT_SECRET só no .env.test — nunca commitar o secret. Sem Auth0 no CI, mocke o AuthGuard no testing module.

A tabela users com passwordHash deixa de ser a fonte de login. Senha e MFA ficam no Auth0, no fluxo de usuário. Se quiser ligar o admin ao domínio depois, grave só auth0Id (sub de um token de usuário) — não a senha, e não o sub de um token M2M.
